# security-review

只读安全审计。目标是找**可被利用**的问题，不是堆清单。不改代码、不提交、不推送。

## 1. 确定范围

- 无参数：审 `git diff`（staged + unstaged），为空时审 `main...HEAD`。
- 给了路径：只审该路径。
- 给了 PR 号：用 `gh pr diff <n>`，并说明是远端内容。

先跑：`git status --short`、`git diff --stat`、`git diff --cached --stat`。

## 2. 读检查单

完整读取同目录的 `checklist.md`，逐项对照。检查单是底线，不是上限。

## 3. 先读项目约束

- 根目录 `CLAUDE.md`
- `.claude/neal/project-context.md`

与代码冲突时以代码为准，但要在报告里指出。

## 4. 输出

一句话结论（能否上线、最大风险），然后逐项：

```
### [严重度] 标题
- 位置：文件:行号 / 方法
- 证据：引用关键代码，标明新增还是原有
- 利用条件：攻击者/用户需要做什么
- 影响：数据、资金、账号、合规
- 最小修复：改哪里、怎么改
- 验证：怎么确认修好了
```

严重度：CRITICAL（可直接利用/泄露凭据/资金风险）、HIGH（确定缺陷）、MEDIUM（防御缺失）、LOW（加固建议）。
状态区分：**已确认**（代码证据）/ **存在风险**（路径成立未跑到）/ **待验证**（缺环境）。

末尾固定：
- **已检查未发现问题**：列出覆盖的检查单条目，避免误以为没查。
- **未验证与限制**：没编译、没抓包、没真机等，逐条写明。

## 5. 红线

- 只读；不要顺手改代码、改配置、跑有副作用的脚本。
- 不要把「风格问题」写成安全漏洞；不确定标「待验证」。
- 不要输出真实的 token、密钥、证书口令（报告里用 `<redacted>`）。
