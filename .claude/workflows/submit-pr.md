# submit-pr 工作流

本工作流践行 **“人来掌舵，AI 来执行”** 的质量保障原则。在将 AI 编写的代码推向主分支前，执行严格的分层防御：

```
[1. 本地状态核查] ➔ [2. 自动化自测门禁] ➔ [3. 独立 AI 预审与风险分级] ➔ [4. 人类掌舵审批 (关键门禁)] ➔ [5. 执行推送与提 PR]
```

---

## 阶段一：建立环境与改动基线

1. **工作区状态确认**：
   - 运行 `git rev-parse --show-toplevel` 确认仓库根目录。
   - 运行 `git status --short`，检查是否存在未提交的代码改动。若有未提交的改动，主动询问用户是否需要先提交。
   - 确认当前分支名与目标 base 分支（默认 `main`，或根据参数指定如 `develop`）。
2. **提取改动范围**：
   - 运行 `git diff --stat <base>...HEAD` 查看文件增删统计。
   - 运行 `git log <base>...HEAD --oneline` 列出本次 PR 包含的提交列表。

---

## 阶段二：自动化自测门禁（测试前置）

AI 必须亲自执行自动化验证，确保代码具备可构建性与基础规范性，**绝不带病提 PR**：

1. **静态检查**：
   - 运行 `make lint`（或 `swiftlint lint --quiet --no-cache XClientLab`），确保 0 Error。
   - 若存在 Error，立即中止流程并修复，不得继续提 PR。
2. **自动化测试**：
   - 运行项目测试套件（如 `make test` 或 `swift test`）。
   - 记录测试耗时与成功用例数，作为后续交付报告的硬证据。
3. **格式化合规**：
   - 运行 `make format-check` 验证格式，如需调整可执行 `make format`。

---

## 阶段三：独立视角 AI 预审与风险分级（降噪与收敛）

脱离写代码时的历史偏见，以**全新只读审查者视角**（参考 `.claude/skills/review-pr/SKILL.md`）对 `git diff <base>...HEAD` 进行独立审查。

### 1. 降噪过滤原则（严禁提出无效噪音）
- **绝不评论代码风格与缩进**：格式问题已由 SwiftFormat 与 SwiftLint 100% 机械兜底。
- **绝不提泛泛而谈的重构偏好**：不提“这里可以写得更优雅”、“建议拆成三个小方法”等无明确收益的建议。
- **必须关注真正致命的问题**：
  - **目标达成度**：本次改动是否真正完成了需求目标？
  - **系统兼容与边界**：是否破坏了已有模块？接口改动是否会导致调用方崩溃？
  - **核心链路隐患**：金额大数计算精度丢失、主线程阻塞、闭包强引用环导致内存泄漏、非幂等接口无条件重试、硬编码密钥/明文敏感日志。

### 2. 问题结构化输出
若发现问题，归入以下两类，并附带 `文件:行号` 与触发条件证据：
- `[Blocker 阻断项]`：必然导致崩溃、金额算错、死锁或构建破坏的严重缺陷。
- `[Risk 潜在风险]`：特定边界条件可能失效或有回归隐患的问题。

### 3. 风险评估与分级
根据修改路径与业务敏感度自动定级：
- 🟢 **低风险 (Low Risk)**：纯 UI 样式、Demo 页面、文档更新、单元测试用例。
- 🟡 **中风险 (Medium Risk)**：普通业务流程、非核心网络接口封装（需 1 位同行评审）。
- 🔴 **高风险 (High Risk)**：涉及交易核心（`TradingCore`）、加密认证、并发多线程与锁、数据库迁移（建议双人审批）。

---

## 阶段四：人类掌舵确认（Human Gate —— 核心安全关卡）

整理一份清晰、中立的 **PR 交付报告** 呈报给人类工程师。

### 报告模板：
```markdown
### 📋 PR 准备就绪报告

- **分支**：`<当前分支>` ➔ `<目标分支>`
- **改动范围**：涉及 X 个文件，+Y 行 / -Z 行
- **自测证据**：
  - SwiftLint: ✅ 通过 (0 Error)
  - 单元/UI测试: ✅ 通过 (X 个用例成功)
- **AI 独立预审结论**：
  - 风险分级：🟢 低风险 / 🟡 中风险 / 🔴 高风险
  - 审查发现：无 Blocker / [或列出 1~2 项关键关注点]
- **拟定 PR 标题**：`<type>: <一句话概括>`
- **拟定 PR 描述**：`<核心改动要点列表>`

---
✋ **请您审查确认**：是否批准并执行提 PR？（回复“确认”继续执行，或输入修改意见）
```

**⚠️ 铁律：在获得人类明确许可之前，严禁自动调用 `git push` 或 `gh pr create`！**

---

## 阶段五：执行推送与创建 PR

人类确认批准后执行：

1. **推送分支**：
   - 检查远端分支：`git push -u origin <当前分支>`
2. **调用 GitHub CLI 创建 PR**：
   ```bash
   gh pr create --base <目标分支> --head <当前分支> --title "<拟定标题>" --body "<拟定描述>"
   ```
3. **交付成果**：
   - 输出 PR 网页链接。
   - 提示后续协同：告知 CI 运行中；若涉及高风险改动，提醒开启功能开关 (Feature Flag) 灰度或通过 Merge Queue 排队合入。
