# fix-and-verify

把「修一个问题」拆成可核对的小步，每一步都有产物，避免"改完就说好了"。
工作流格式以本机 Claude Code 的校验结果为准；若 `/workflows` 报字段不识别，只保留 `name`、`description` 与下方步骤文本即可。

## 输入
- 问题：描述、issue 编号/链接、崩溃日志或报错原文。
- 可选：期望行为、影响范围、必须保持不变的约束。

## 步骤

### 1. 建立事实
- `git rev-parse --show-toplevel` 定位仓库根；`git status --short` 确认工作区。
- 读 `CLAUDE.md`、`.claude/neal/project-context.md`。
- 用关键词/堆栈定位相关文件与调用链，先读代码再判断。
- 产物：涉及的文件清单 + 调用路径。

### 2. 复现或确认
- 能命令行复现的（编译错误、SwiftPM 测试、脚本）先复现并保存原始报错。
- 不能复现的写清原因（缺环境/缺账号/需真机），标注「未复现」。
- 产物：复现命令 + 原始输出，或未复现说明。

### 3. 根因
- 写清触发条件、调用路径、为什么现在暴露。
- 区分「已确认」（有代码/日志证据）与「推测」（需验证）。
- 产物：一段根因说明 + 证据位置（文件:行号）。

### 4. 最小修复
- 只改与根因相关的代码，保持 diff 可读；不顺手重构、不清理无关告警、不改 `Pods/`。
- 金额/精度只用 String 大数；非幂等接口不加重试；主题 key 三处同步；国际化补全语言。
- 产物：`git diff --stat` + 每个文件的改动理由。

### 5. 验证
- 按 `.claude/rules/testing.md`：SwiftPM 包跑 `swift test`；主 App 跑一次 `xcodebuild ... build`（或说明为何不跑）。
- 自查清单：线程/生命周期、订阅退订、空态与错误态、深色模式、切换语言、退登、前后台。
- 产物：命令 + 结果；跑不了的列「未验证 + 最小手动步骤」。

### 6. 交付
- 中文结论先行：根因一句话、改了哪些文件（路径:行号）、验证结果、未验证项、手动回归建议。
- 不编造测试/性能数据；不提交、不推送，除非用户明确要求。

## 失败处理
- 编译失败先看第一条错误，不要一次贴几十条日志。
- 私有 pod / 证书 / 模拟器缺失导致无法验证时，明确说明并给出用户侧一条命令，不要绕过或改 Podfile。
