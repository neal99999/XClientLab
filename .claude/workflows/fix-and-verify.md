# fix-and-verify 工作流

本工作流用于规范日常缺陷修复与疑难问题攻坚，践行 **“证据先行、最小改动、测试回归”** 的工程纪律，杜绝“改完就盲目宣称修好了”的侥幸行为。

---

## 阶段一：建立现场与事实取证

1. **工作区状态确认**：
   - 运行 `git rev-parse --show-toplevel` 与 `git status --short` 检查本地基线；
   - 确认当前正在处理的 Issue 描述、崩溃日志（Crash Log）或卡顿指标。
2. **客观现场取证**：
   - 若为崩溃问题（如 UAF / 0x1d）：借助 MCP 执行 LLDB 批处理，读取崩溃线程 `thread list`、寄存器 `register read x0 x1 x2 x3 lr pc`；
   - 若为主线程卡顿问题：读取 `HitchMonitor` 指标（`worstHitchMs` 与 `blockedTotalMs`）；
   - 若为测试用例失败：运行 `make test` 或 `xcode_test` 保存原始失败日志。
   - 产物：原始报错日志与涉及的符号调用链。

---

## 阶段二：根因分析（Root Cause Analysis）

1. 准确定位问题发生的源头文件与行号（`文件:行号`）；
2. 明确给出触发条件（例如：弱网 TCP 假连接、多线程未加锁同时读写 `counter`、Timer 释放后回调仍访问野指针）；
3. 严格区分：
   - **已确认结论**（有寄存器、调用栈或测试失败直接证明）；
   - **推测假设**（需要进一步通过单元测试或断点印证）。

---

## 阶段三：最小修复（Minimal Surgical Fix）

1. **坚决克制改动范围**：
   - 只改动与本次根因直接相关的核心代码，保持 `git diff` 极致清晰与可审查；
   - 严禁顺手大范围重构、严禁顺手格式化无关文件；
   - 绝不改动 `Packages/` 源码底层契约（除非属于契约缺陷）。
2. **严守编码红线**：
   - 资金计算必须用 `String`/`Decimal`；
   - 异步回调必须有 `[weak self]`；
   - 共享状态必须收敛进锁或 Actor。

---

## 阶段四：验证与防倒退（Regression Testing）

1. **本地测试门禁**：
   - 运行 `make lint` 确保 0 语法与格式报错；
   - 运行 `make test`（执行 44 个单元与 UI 测试），确保所有既有用例全部通过；
   - 若改动涉及 UI 组件，确认 `ComponentSnapshotTests` 快照比对达到 `0.00% PASS`。
2. **补充针对性单测**：
   - 为本次 Bug 补充至少 1 个能够重现该边界条件的单元测试用例，防止未来重构时问题复现。

---

## 阶段五：结构化交付报告

整理交付报告呈报：
- **根因一句话总结**；
- **核心修改清单**（`git diff --stat` 与关键变更解释）；
- **客观验证证据**（单元测试执行数、耗时、修复前后的指标对比）；
- **回归建议**（提醒人工审查需要关注的周边模块）。
