## 0. 这份稿子的事实边界（先说清楚，别现场破功）

| 能说 | 不能说 |
| --- | --- |
| `XClientLab` 是独立搭建的 iOS 性能与稳定性沙盒，本机可运行，BUILD / TEST 均通过 | 不能说它"已在生产验证"或"有 CI" —— 它没有 git 仓库，也没有流水线 |
| `trade-demo` 有真实 GitHub 私有仓库、PR、Actions 运行记录、8/8 业务测试 | 不能说已经灰度、已上架、有真实用户 |
| AI 闭环是**单人闭环**，有完整设计，团队级落地尚未验证 | 不能说"已经在团队落地""效率提升 X%" |
| K 线渲染 55 FPS / CPU −20% 来自上一份工作的真实项目 | 不要把 `XClientLab` 的演示数据说成线上指标 |

**一句话总纲**：能证明的给证据，不能证明的给设计，两边都不含糊。

## 四、第 3–8 分钟：动机三问

### 4.1 为什么离开待了六年的公司

> "六年其实挺长的，走的原因不是有什么具体矛盾。交易所这个方向我做了很久，核心模块基本都摸过一遍，再往后更多是重复和经验复用。我想去一个对'工程正确性'要求更高、同时团队规模更小、我能承担更完整责任的地方。"
>
> "另外一点比较个人：今年这几个月我在做 AI 辅助研发的闭环，越做越觉得这件事需要在一个真实团队里才能验证——一个人做出来的是'我能跑通'，放进团队才会暴露协作和门禁的问题。这也是我想换环境的原因之一。"

**不要说**：前司管理混乱、加班多、业务不行、领导不行。一个字都别评价。

### 4.2 这八个月空窗期在做什么（他一定会问，主动交代）

> "三月到现在，我在做两件事。
>
> 第一件是把 AI 辅助研发从'会用工具'推进到'有门禁的流程'：需求卡先写清楚验收和非目标，业务测试由我先定预期、再让 AI 实现，CI 跑确定性检查，AI 只做审查不做放行，合并和发布必须人签。这些不是纸上的，待会儿我可以直接跑测试和开 CI 页面给您看。
>
> 第二件是 `XClientLab`，一个 iOS 的性能与稳定性沙盒。我把它当成'可复现的证据库'——每个场景都先故意制造一个可复现的问题，再用 Instruments、LLDB、指标面板把证据拿出来。因为面试里最容易讲虚，我想让它变成能跑的东西。"

### 4.3 为什么是 Pepperstone / 为什么这个岗位

> "我看 JD 的时候有三个点对上了。第一是交易正确性被放在很前面——下单、持仓、保证金、精度，这些是我做了六年的东西，也是我认为最不能出错的地方。第二是实时链路，WebSocket、高频刷新、重连和弱网，这是我最能拿证据的一块。第三是 JD 里专门写了 AI 工程协作，还提到 Agent、MCP、上下文文件——这块我今年正好在做，而且是当工程问题在做，不是当玩具。"

### 4.4 期望与到岗

> "级别上我希望是能独立负责一块业务的资深工程师，同时愿意承担 code review 和带新人；我不想空降做管理。到岗我随时可以。"

## 五、第 8–19 分钟：Demo 第一幕 `XClientLab`（11 分钟）

### 5.0 定位句（30 秒，每次演示前必说）

> "这是一个我自己搭的 iOS 实验室。它不是产品，是一个证据库：每个场景我都先制造一个可复现的问题，然后用工具把证据拿出来，最后说清真实工程里怎么修、AI 在里面能干什么、不能干什么。底部五个 Tab 是性能、异常、交易所、AI-Native、架构，您想先看哪个都行——我建议从交易所开始。"

**如果他直接点**：他想看哪个就看哪个，用第七节的场景卡接。不要抢回控制权。

### 5.1 交易所 3.1 弱网重连（4 分钟）

[进入 交易所 → 3.1 弱网 WS 重连]

> "这个场景模拟弱网下的 WebSocket 重连。策略是：base 从 0.5 秒开始指数增长，封顶 8 秒，每次加 ±20% 的抖动，重试 6 次还没成功就进 EXHAUSTED 状态，停下来。"

[点"制造断线"]，边点边说：

> "我现在手动触发一次 1006 断线。您看这里 NEXT DELAY 在变——0.5、1、2、4，封顶 8。加抖动是因为如果所有客户端用同一个退避曲线，网关恢复的瞬间会被同时打一遍，那是重连风暴。"

[等它走到 EXHAUSTED]

> "第六次之后它停了，不重试了。这一点很重要：无限重试看起来'更健壮'，实际上是掩盖问题，还会在弱网下持续打网关。停下来之后应该交给 UI 提示 + 用户手动重试 + 后台补偿。"

**追问预备**
- Q：**重连成功就代表数据对了吗？** → 不代表。连接恢复只是传输层恢复，订阅要重新确认，行情要重新同步快照，中间可能有缺口。我在这块的做法是：连接状态、订阅状态、数据新鲜度是三层，不能混。
- Q：**心跳正常但某个品种不推数据怎么办？** → 心跳只证明连接活着。要有按订阅维度的数据陈旧检测（比如超过 N 秒没有更新就标记 stale 并重新订阅），不能让 UI 一直显示旧价格。
- Q：**为什么是 6 次？** → 是演示值，不是真理。真实参数要按业务容忍度和网关容量定，而且要有上限和人工兜底。

### 5.2 交易所 3.2 高频盘口（3.5 分钟）

[进入 3.2]

> "这个场景模拟高频盘口：83 条每秒的全量推送。如果每条都直接刷 UI，一定会卡。我的做法是三层：接收和解码一层，领域状态归并一层，主线程只提交展示快照。合并用单槽节流——只保留最新一版待提交，中间的直接丢掉，因为盘口是'最新值有效'的数据。"

[跑一轮，指着 hitch 指标]

> "这里能看到 hitch 指标，60 和 120 赫兹的掉帧统计。同时我保留了推送条数和实际提交次数的对比——您可以看到提交次数远小于推送次数。"

> "这里有个容易踩的坑我想主动说一下：降低刷新频率是有效优化，但它会掩盖数据陈旧。所以我不会只说'帧率上去了'，我会同时看三个东西：帧率、数据时效、队列有没有积压。如果队列一直在涨，说明你不是优化了，是把问题往后推了。"

**追问预备**
- Q：**丢中间帧会不会丢成交？** → 不会，因为盘口是快照语义，最新一版包含全部信息。但成交明细是事件流，语义不同，不能同样处理——这是我特意区分的地方。
- Q：**怎么证明不是靠降频糊弄？** → 看时效和积压两个指标，不是看 FPS。

### 5.3 AI-Native 4.1：MCP 通道纪律（3.5 分钟，全场最值钱）

[进入 AI-Native → 4.1]

> "这一段是我最想给您看的，因为它回答的是'AI 到底怎么进研发流程'这个问题。
>
> 很多人用 AI 的方式是：把命令丢给模型，模型直接执行。在调试场景里这很危险——LLDB 的 attach、`bt all`、批量断点，一旦模型判断错了，它会把调试现场搞乱，你连原始状态都回不去。
>
> 我的做法是把纪律写成状态机：这个通道有明确的状态，从空闲到就绪到运行到停止，每一步都有前置条件。"

[点"按纪律执行批处理"]

> "现在它按顺序走到 STOPPED，再批量执行 5 条命令。您看每一步都有日志。"

[在 running 阶段点"越权直发 bt all"]

> "现在我故意越权，在它不允许的阶段直接发 `bt all`——被守卫拦住了，而且计数加了 1。
>
> 这一下的意义是：**AI 不是被信任，是被约束**。权限边界写在代码里，不写在提示词里。提示词可以被绕过，代码里的守卫不行。"

**追问预备**
- Q：**这跟团队协作有什么关系？** → 关系很大。单人时靠自觉，团队里必须靠机制：谁可以执行、什么阶段可以执行、执行记录在哪。我这一层是演示版，但结构是团队级的。
- Q：**这么做是不是太重、拖慢效率？** → 只对破坏性操作重。读代码、写测试、生成桩这些不设这个门。我的原则是：不可逆的动作要门禁，可逆的动作放手。

### 5.4 降级为"一句话 + 截图"的场景（他问再说）

| 场景 | 一句话 |
| --- | --- |
| 性能 1.1 主线程卡顿 | "故意把 6000 条 JSON 解析和正则匹配放主线程，极端档单轮阻塞超过 500 毫秒，用 Time Profiler 取证，真实修复是分块 + 后台队列 + 可取消。" |
| 异常 2.1 UAF | "DispatchSourceTimer 释放瞬间的野指针，`EXC_BAD_ACCESS`、地址 `0x1d`，现场只有系统栈；用 LLDB 批处理把现场固化成可复现的取证步骤。" |
| 异常 2.2 并发踩踏 | "多线程非原子读写的丢失写，用 TSan 抓数据竞争。" |
| 架构 5.1/5.2 | "本地 SPM 包单向依赖：契约层零依赖，实现层依赖契约，App 只做组装；换实现只改一行注册。" |

**注意**：2.1 / 2.2 会真的崩溃 App。远程演示**不要现场跑**，用录屏或截图，否则重启模拟器要一分钟。

## 七、六个"现场改"场景卡

他说"换个场景"时，从这六张里挑一张，每张 2–3 分钟。**操作要脱稿，讲解要一句话说清取舍。**

### 卡 1：报价有效期改成 2 秒
- 操作：`PUT /admin/config {"quoteTtlMs": 30}` → `npm test` 或直接 curl 下单
- 讲解："过期拒绝在服务端，客户端只做体验；两边都校验，但以服务端为准。"
- 边界："这是服务端时间，不是客户端时间——客户端改系统时间不应该影响判定。"

### 卡 2：重复下单
- 操作：打开 TRADE-03 用例，5 个并发请求同一 `clientOrderId`
- 讲解："1 个 accepted、4 个 duplicate，而且 5 个响应指向同一个服务端订单号。幂等键是 `userId + clientOrderId`，唯一约束在数据库层，不是靠内存去重。"
- 边界："按钮防连点只能降低概率，替代不了服务端幂等。"

### 卡 3：客户端超时但服务端接了单
- 操作：注入 `drop_response`，下单，然后按 `clientOrderId` 查单
- 讲解："HTTP 超时不等于业务失败。进入'结果未知'状态，用原编号查单收敛，绝不换一个新编号重下。"
- 边界："查单暂时查不到也不能判定失败，要有重试和人工兜底。"

### 卡 4：重连退避上限调小
- 操作：回到 `XClientLab` 3.1，改参数或直接演示 EXHAUSTED
- 讲解："上限 + 抖动 = 防重连风暴；预算耗尽要停，停下来之后靠什么兜底。"
- 边界："参数是演示值，真实值按网关容量和业务容忍度定。"

### 卡 5：盘口节流从 1 帧改成 3 帧
- 操作：`XClientLab` 3.2 调整提交频率，看 hitch 和提交次数
- 讲解："更省 CPU，但时效变差；所以要同时看帧率、时效、积压三个数。"
- 边界："这是展示层优化，不改变业务数据。"

### 卡 6：加一个撤单状态怎么改
- 操作：**不写代码**，在纸上/白板上画状态机
- 讲解："提交、受理、部分成交、全部成交、撤单处理中、已撤销、拒绝。撤单接口的'已接收'和'已撤销'是两回事；终态之后来的旧推送要按版本或成交 ID 丢弃，不能按到达顺序覆盖。"
- 边界："状态名和合法转换以服务端契约为准，我不自己发明。"

## 八、第 26–37 分钟：追问库（按可能性排序）

### 8.1 团队级 AI 协作（你的真空洞，必然被问）

> "我目前的闭环是单人闭环，这点我如实说，没有团队数据。
>
> 但我把它拆成了可以往团队推的三层：
> 第一层是**共享上下文**——项目结构、可运行命令、架构约束、不能碰的边界，写成文件放在仓库里，让所有人的 AI 输出有同一个前提。
> 第二层是**流程沉淀**——重复的事写成 Skill，比如'加一个状态字段'该改哪几个文件、跑哪个测试，让不同人跑出一样的结果。
> 第三层是**门禁**——AI 可以写、可以审，但合并和发布必须过测试和人工；资金相关的改动必须人签。
>
> 第三层是团队级和单人级最大的区别。单人时你自己就是门禁，团队里门禁必须是机制，而且机制要能被绕过检测——我的做法是本地 hooks 只做提示，真正的门禁放 CI 和分支规则上。"

**加分补一句**：
> "如果让我在一个团队落地，我不会先推工具，我会先推两件事：一个能跑起来的测试入口，和一份不超过一页的上下文文件。工具是最后一步，因为前两步没做，AI 只会把混乱放大。"

### 8.2 单测：你怎么决定测什么

> "看后果，不看覆盖率。我的分法是三层：
> 第一层是**业务规则**，必须写——精度和单位、幂等、状态转换合法性、权限边界。这类错了是要赔钱的，所以用测试锁死。
> 第二层是**时序和并发**，尽量写——超时、乱序、重复、丢响应。
> 第三层是**UI 和布局**，少写——用截图和人工验收更划算。
>
> 覆盖率我当参考不当目标，因为覆盖率能刷。"

### 8.3 CI/CD 你到底做过没有

> "做过服务端的，iOS 端的只到本地脚本。区别我说清楚：
> 服务端这个仓库是完整跑的——分支、PR、Actions、失败会红。
> iOS 这边有 `make build / test / lint`，但没接 macOS runner，原因是没开发者账号，也没有真实的发布链路可验。
> 所以我的能力边界是：**能设计并跑通一条最小流水线，但没有在真实团队里维护过半年以上。**"

### 8.4 流程是不是太重（他很可能觉得你过度设计）

> "全量流程是演练用的完整度，不代表我主张团队这么跑。真实团队我只先落三件事：业务单测、PR 必跑 CI、功能开关。Jira 自动流转、Slack 通知、分阶段灰度，都要等有第二个真实需求再上。
>
> 流程的目的是兜住资金类错误，不是把节奏拖慢。如果一套流程让人开始绕过它，那套流程就是错的。"

### 8.5 带人 / code review

准备一个**具体的人 + 具体的事**，不要说流程。模板：

> "我带过一个刚转 iOS 的同学。他最初的问题是改 A 功能会把 B 功能弄坏，因为不理解模块边界。我的做法不是替他改，而是让他每次改动前先写'影响面'——入口、调用方、共享状态——写不出来就先别动手。三个月后他提交的 PR 基本不需要我做结构性返工。"
>
> "我现在 review 的习惯是：结构问题当面说，细节问题留在 PR 里；资金相关的改动我一定自己跑一遍。"

### 8.6 交易正确性（他若懂业务会深挖）

> "三条底线：
> 一，**超时不等于失败**，用业务请求标识收敛，不换编号重下。
> 二，**精度和单位显式建模**，价格 tick、数量 step、舍入方向都要有契约，不能靠 Double。
> 三，**客户端和服务端都校验，但以服务端为准**，客户端只做体验。"

### 8.7 失败 / 事故

用真实经历，结构固定：影响 → 止损 → 定位 → 修复 → 验证 → 改进。
**别选"其实不是我的错"的案例**，EM 要的是你认账的样子。

### 8.8 冲突

> "先分清争的是数据口径、产品行为、还是实现方式。口径问题找数据源，产品行为找产品负责人，实现方式我来定但要给证据。我最不想做的是把'我觉得'和'你觉得'对着吵——先把事实摆出来，很多分歧自己就没了。"

## 九、第 37–42 分钟：反问（逐字稿，三个）

### 反问 1（最重要）

> "团队现在 AI 用到什么程度？是各自为战，还是有统一的上下文和规则沉淀？"

**为什么问**：直接对上你的 gap，同时说明你关心的是团队级落地而不是个人炫技。他答什么你都能接。

### 反问 2

> "如果我加入，前六个月只做成一件事，您希望那件事是什么？"

**为什么问**：问成功标准，比问团队介绍高一个段位。他的答案就是你入职后的考核表。

### 反问 3（收尾）

> "聊下来，您对我还有什么顾虑？尤其是 AI 和测试这两块——第一轮反馈里提到过，我想知道您怎么看，我还需要补什么。"

**为什么问**：第一轮的顾虑已经写在纸上了，你等于拿到了答案，还多一次解释权。听完别辩解，说"明白，这块我确实只有单人经验，我的补法是……"。

### 备选（时间富余时挑一个）

> "交易正确性现在靠什么兜底？客户端和服务端的校验边界怎么划？"
> "iOS 团队现在多少人？和 backend、QA 怎么协作？发布节奏是怎样的？"
> "您怎么看 AI 生成代码在资金相关模块的边界？团队现在的评审要求是什么？"

**不要问**：加班多不多、薪资多少（留给 HR）、JD 上写了的、"我表现怎么样"。

## 十一、红线清单（说错一句就掉档）

1. 不说"生产落地""零缺陷""效率提升百分之多少"——没有证据。
2. 不说前公司代码、数据、内部系统名；`trade-demo` 是独立实现，讲的时候点明。
3. 不把设计说成做过：Jira / Slack / Figma 没接就是没接。
4. 不说 `XClientLab` 有 CI —— 没有。要证 CI 就切到 `trade-demo`。
5. 不主动声称 SwiftUI 深度经验 —— `XClientLab` 是 UIKit + MVVM；JD 是"SwiftUI 和/或 UIKit"，如实说主 UIKit，SwiftUI 用过但没到架构级。
6. 不评价前司、不评价其他候选人、不抱怨流程。
7. 被问不会的，直接说"这块我没有实操，我的理解是……"，然后停。**不要编，编了一定被追问穿。**
