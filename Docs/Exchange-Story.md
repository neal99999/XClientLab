## 1. 案例一：极端行情下的渲染性能重构

### 1.1 现象（Situation）

- 非农、大行情时，服务端每秒推送 100+ 条 Tick。
- 旧代码“来一条刷一次”：指标计算、K 线重绘、盘口刷新全部在主线程。
- 结果不是“图表有点卡”，而是：
  - K 线 20–30 FPS；
  - 主线程单次提交 20ms 量级；
  - 用户点「市价平仓」，事件在 main queue 里排队超过 1 秒；
  - 用户在剧烈行情里因为滑点真实亏钱，客诉集中到“点了没反应”。

### 1.2 难点（Difficulty）

1. **不能简单“丢数据”**：盘口和 K 线要的是最新状态，但成交、下单回报不能丢。
2. **不能把所有东西都扔后台**：UIKit / Core Graphics 的提交仍然要在主线程，关键在于“主线程只做最少的、最新的那一帧”。
3. **指标计算是重复劳动**：MA / MACD 每来一条都全量重算，计算量随窗口线性增长。
4. **屏幕外也在画**：历史 K 线、网格、看不见的柱子都参与重绘，GPU/CPU 都在做无效功。
5. **交易链路有优先级**：渲染可以降级，下单点击不能排队。

### 1.3 动作（Action）

**第一步：算力搬家 + 版本凭证**

- 指标计算全部移到后台并发队列。
- 每次计算带一个单调递增的 `version`；主线程只接受比当前更新的版本，旧结果直接丢弃。
- 这样即使后台算得慢，UI 也不会被“过期帧”拖住。

**第二步：视口裁剪 + 脏矩形**

- 只绘制当前 `Visible Rect` 内的 K 线；屏幕外的历史数据不参与本次绘制。
- 最新一根 K 线用 `setNeedsDisplayInRect` 做局部脏矩形重绘。
- 背景网格、坐标轴走离屏缓存，不随每帧重画。

**第三步：100ms 时间窗聚合（Throttling）**

- 在数据源和 UI 之间加一个 100ms 的聚合窗口。
- 窗口内收到的多条 Tick 合并成一个标准的 High / Low / Close 包再提交。
- 人眼不需要 100Hz 的重绘；100ms 对应 10Hz 的视觉更新，已经足够跟手。
- 这不是“丢业务数据”：原始 Tick 仍然进入行情缓存/指标计算，只是 UI 按时间窗消费。

### 1.4 结果（Result）

| 指标 | 改造前 | 改造后 |
| --- | ---: | ---: |
| 极端行情帧率 | 20–30 FPS | 55+ FPS |
| 下单点击延迟 | >1s | <16ms |
| CPU 占用 | 基线 | 约 −20% |
| 客诉 | 卡顿/滑点集中 | 归零 |

### 1.5 现场怎么演

进入「交易所专项 → 案例一」：

1. 默认「旧链路 · 全量重绘」，点 `START STRESS`。
2. 等 2–3 秒，读出 `FPS ~40`、`MAIN THREAD ~21ms`、`ORDER P95 1000+ms`、状态“订单事件排队 >1s”。
3. 点「市价平仓 · 测延迟」，说明“这不是按钮坏了，是 main queue 在排队”。
4. 点 `STOP`，切「重构后 · 聚合 + 裁剪」，再 `START STRESS`。
5. 对照 `MAIN THREAD` 降到个位数、订单 P95 回到 16ms 内，讲三步改造。

> 演示数据是模拟器上真实跑出来的，不等于线上生产数字；线上的 55 FPS / −20% CPU 来自上一份工作的真实项目。

### 1.6 可能的追问

**Q：为什么是 100ms，不是 16ms？**
> 16ms 是 60Hz 的帧预算，不是“数据必须每 16ms 更新”。K 线是低频视觉信号，100ms 聚合能显著削峰，又不影响看盘；盘口/成交回报走独立的高优先级通道，不能被这个窗口吞掉。

**Q：后台算完，主线程还是要提交，凭什么不卡？**
> 卡的不是“提交”这个动作，而是“每次都全量算 + 全量画”。版本凭证保证只提交最新结果，裁剪和脏矩形把每次提交的面积降下来，100ms 聚合把提交频率降下来，三件事一起才有效。

**Q：丢掉中间帧，指标不会错吗？**
> 指标基于原始 Tick 在后台算，聚合只影响“UI 拿哪一帧”。如果业务要求每一帧都可追溯，就把聚合层做成可回放缓冲，而不是直接覆盖。

**Q：为什么不用 Metal / 自绘替换？**
> 先算清楚瓶颈在 CPU 主线程还是 GPU。这个 case 的主因是主线程计算和重绘，不是 GPU 填充率；上 Metal 是成本更高的解法，先把算力和绘制面积降下来。

## 2. 案例二：跨国弱网 TCP 假连接 + 订单状态竞态

### 2.1 现象（Situation）

**坑 A：TCP 假连接**

- 用户进电梯、跨国漫游、Wi-Fi 切 4G。
- 系统底层没有立刻回调断开，客户端以为长连接还活着。
- 实际上行情早停了，用户看到的是“冻住的盘口”。

**坑 B：订单状态倒流**

- 弱网下用户下单，HTTP 响应慢。
- 后端通过 WS 先推「已成交」。
- 慢一步的 HTTP 返回「挂单中」，把页面刚显示的「已成交」覆盖回去。
- 用户看到订单状态反复横跳，严重时以为没成交而重复下单。

### 2.2 难点（Difficulty）

1. `Reachability` 只代表“有网卡”，不代表“链路可达”；TCP keepalive 的时间尺度是分钟级，业务等不起。
2. WS 和 HTTP 是两条通道，**不保证到达顺序**；不能假设“后发的 HTTP 一定比先发的 WS 新”。
3. 订单状态是有业务语义的：`pending → filled` 可以，`filled → pending` 不允许。
4. 重连不能打爆网关：需要退避、抖动、上限和备用节点。

### 2.3 动作（Action）

**网络层：应用层心跳 + 死链探测**

- 客户端每 5s 主动发一个轻量 Ping。
- 连续 2 次没有 Pong，或超过 10s 没有任何下行数据，判定为假连接。
- 立即强杀旧连接，触发智能重连：DNS 测速 + 备用节点，避免所有客户端同时打回原节点。

**业务层：Sequence 版本号 + 单向状态机**

- 后端给每个订单事件带一个单调递增的 `Sequence`。
- 客户端只接受比本地更新的版本；旧版本直接丢弃。
- 订单状态只允许 `pending → filled` 单向流转，任何迟到事件都不能把 `filled` 回滚。
- 状态机是“最后防线”：即使版本号因为服务端 bug 异常，也不能出现已成交回到挂单中。

### 2.4 结果（Result）

| 指标 | 结果 |
| --- | --- |
| 电梯 / 切网自愈 | 平均 <3s |
| 订单状态回滚 | 0 |
| 账实一致 | 100% |
| 状态错乱客诉 | 归零 |

### 2.5 现场怎么演

进入「交易所专项 → 案例二」：

1. 保持「开启心跳探测」，点「注入断网 · 电梯场景」。
2. 观察 `Pong 丢失 1/2 → 2/2 → 强杀 → RECONNECTING → 已恢复（自愈 2.8s）`。
3. 关掉心跳再注入一次，观察它停在“假连接”，说明为什么不能相信系统回调。
4. 保持「开启版本号保护」，点「注入乱序事件 · HTTP 慢响应」。
5. 观察 `WS filled seq=12` 先到，随后 `HTTP pending seq=9` 被判定为旧版本丢弃，状态保持「已成交」。
6. 关掉版本号保护再注入一次，观察状态回滚到「挂单中」，说明为什么需要客户端兜底。

### 2.6 可能的追问

**Q：为什么不用 TCP keepalive？**
> 太慢，且受系统/NAT 影响；业务需要秒级发现，必须在应用层做主动探测。

**Q：心跳会不会很耗电/流量？**
> 5s 一次轻量 Ping，包很小；相比“假连接导致用户看到冻盘、重复下单”，成本可以接受。也可以按前后台状态动态降频。

**Q：WS 和 HTTP 都带 sequence，谁生成？**
> 服务端统一生成，按账户/订单维度单调递增；客户端只做比较和拒绝，不自己造版本。

**Q：如果服务端 sequence 回绕/重复？**
> 协议上要求单调，客户端做防御性拒绝；同时用订单状态机兜底，任何回滚都不可达。

**Q：为什么状态机只允许 pending → filled？**
> 交易所订单还有 partial-filled、canceled 等状态，完整状态机更复杂；这个 case 只展示最关键的“不可回滚”原则，真实实现会把合法迁移表显式列出来。

## 4. 事实边界

- 55+ FPS、<16ms、CPU −20%、<3s 自愈、100% 账实一致，来自上一份交易所工作的真实项目复盘。
